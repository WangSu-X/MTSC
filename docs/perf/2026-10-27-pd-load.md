# MTSC load 前移与 D save 默认关闭：GPU 对照实验

实现提交：`42ffa69 perf(connector): start KV loads before forward`。
基线提交：`77f44ff`。实验使用两份独立代码快照，没有加载旧实验目录中的
instrumentation/runtime overlay，没有修改系统包。

本机三轮对照没有测出性能提升：输出吞吐变化 -0.26%，平均 TTFT 变化 +1.67%。
这是 A6000/TCP、并发 4 的结果，不代表 950/Ascend 的结果。两组按先 baseline 三轮、
再 candidate 三轮执行，未做交错或显著性检验；小幅差异不足以证明稳定的性能变化。

## 修改范围

- `MTSCConnector.start_load_kv()` 在 forward 前将加载 metadata 交给 worker。
- `MTSCWorker.start_load_kv()` 登记计划并提交异步 Store GET。Store miss 的 PD
  接收也立即提交；Store hit 仍在 GET 终态后按实际边界 A 发起后缀接收。
- `get_finished()` 不再重复提交 GET，仍负责完成聚合、失败块、后续阶段推进和
  forward 后的保存、P source-ready 发布。抢占 fence 保留。
- 已有 `kv_connector_extra_config.mtsc_decode_save` 的默认值从 `true` 改为 `false`。
  显式 `true` 恢复保存完整生成块的行为，P 保存和 D 加载不受影响。

## 正确性验证

CPU 环境 `vllm==0.23.0+cpu`、Python 3.10：252 项测试通过，包括新增的 18 项
加载 hook 顺序、空计算 step、部分 GET 失败后 PD 补齐、抢占重试以及 D save
默认值/显式开关/producer/consumer/both 角色测试。修改文件通过 Ruff check/format
和 `git diff --check`。

两份代码分别在 GPU 上执行以下端到端检查，temperature=0、生成 16 tokens，
每种长度先清空 Store，再比较独立全计算、冷 PD、热 PD 的完整输出文本：

| Prompt tokens | 冷 PD 的 Store / PD tokens | 热 PD 的 Store / PD tokens | 输出一致 |
| --- | --- | --- | --- |
| 1024 | 0 / 1024 | 1024 / 0 | 两个版本均一致 |
| 1031 | 0 / 1031 | 1024 / 7 | 两个版本均一致 |

独立全计算直接调用 D，使用独立 cache salt。检查了实际 D load reports，
不只检查 HTTP 200：每个请求均 `workers=2/2`、`status=ok`，同时覆盖实际 Store GET
和实际 PD 加载。六轮性能回放的 162 个 D 加载报告也全部成功、无 Store/PD error，
每个请求的 local + Store + PD tokens 与 target 一致。

## 性能配置与方法

沿用 `workerspace/scripts/mtsc` 与 `workerspace/exp/mtsc/datasets/trace_024` 的
模型、数据和主要服务参数，使用新增的 `benchmarks/pd_load_perf.py` 启动隔离服务。
客户端用 aiohttp 回放同一批 raw chat payload，不使用 AIPerf，因此不直接比较旧的
AIPerf 数字。每条 trace 的三个 turn 按完成顺序串行，不同 trace 共享并发限制。

## 复现

使用上述本地快照、模型和既有数据。每次选择不存在的 output 目录；先完成一组，
再运行另一组，不能同时占用相同 GPU 和端口。脚本使用 Master 50097/8097/9027、
P 8170、D 8270、bootstrap8970、proxy8370，不复用旧实验服务。

```bash
GPU_PY=/workspace/MTSC/workerspace/scripts/mtsc/.venv/bin/python
PERF_ROOT=/workspace/MTSC/workerspace/exp/perf_20261027

"$GPU_PY" benchmarks/pd_load_perf.py \
  --source "$PERF_ROOT/baseline" --output "$PERF_ROOT/baseline-rerun" \
  --python "$GPU_PY" \
  --master /workspace/MTSC/workerspace/scripts/mtsc/.venv/lib/python3.12/site-packages/mooncake/mooncake_master \
  --model /root/.cache/huggingface/hub/models--Qwen--Qwen3-4B/snapshots/1cfa9a7208912126459214e8b04321603b3df60c \
  --dataset-dir /workspace/MTSC/workerspace/exp/mtsc/datasets/trace_024/sessions \
  --rounds 3 --decode-save off

# 上条命令退出后，将 source 改为 candidate、output 改为 candidate-rerun，
# --decode-save 改为 default，再执行一次。

"$GPU_PY" benchmarks/summarize_pd_perf.py \
  "$PERF_ROOT/baseline-rerun" "$PERF_ROOT/candidate-rerun" \
  --output "$PERF_ROOT/comparison-rerun.json"
```

脚本的 `--rounds 0` 只跑 GPU E2E；`--decode-save on` 可显式开启 D 保存。
snapshot 的源文件 SHA256、数据 SHA256 和完整服务命令均保存在输出目录。

## 后续优化点

以下均未在本次实现，避免混入其他变量。

1. **全命中时让 D 完成与 P cleanup 解耦。** E2E 的 1024-token 热请求已经
   `store_tokens=1024, pd_tokens=0`，但两个版本仍分别记录约 136.7、141.0 ms 的
   PD 阶段耗时。当前空 PD 仍等 P ready；可以让 D 直接完成加载，另行发送幂等的
   skipped/release 通知。以上是单次功能样本，不是可直接外推的加速比例。
2. **消除 completion 查询的主线程同步往返。** `kv_transfer.py:poll/take_errors`
   每步通过 `run_coroutine_threadsafe(...).result()` 等后台 loop；D 至少有两次。
   可将完成和错误合并到线程安全队列，主线程非阻塞收取，保持错误与终态的一致性。
3. **P ready event 后台等待。** `worker.py:update_finished_metadata()` 的
   `ready.synchronize()` 在主线程执行，且 event 记录在当前 forward 后。应记录
   正确源 step 的完成 event，并在发布线程等待，避免把其他请求计算纳入依赖。
   必须保留抢占、取消和源块复用前的 fence。
4. **先做两个低风险 CPU 去重。** 将 `_build_request_transfer_params()` 中与
   region 无关的 block 校验、连续块分组提到 region 循环外；缓存每个 transfer
   plan 的 Store candidate block 集合，避免 `get_finished()` 每步重新切片和构造
   set。优先用 CPU profile 验证占比。
5. **分解 Store/PD 阶段计时，再调整并发。** 当前 store_ms 包含线程池排队与
   completion 观察延迟，pd_ms 包含 P ready、控制通信等，均不是纯带宽指标。
   补齐 submit/work-start/I/O-done/poll 和 P-ready/write-start/write-done 后，
   再决定是否调 `mtsc_store_load_workers`、做跨请求合批或共享 TE。
6. **独立 sender task 配置及 ready 队列。** 将协程数与 TE 线程数解耦，等待
   ready 不占用实际传输槽，同时对总 inflight 做背压。本轮并发仅 4，不能用于
   证明默认 20 个 sender task 是瓶颈，需要 c32/c64 的专门实验。
7. **Lookup 先测，不因按 request 查询就重写。** 分开记录 queue_ms、服务耗时
   和 key 数。如果排队明显，再做多请求合批、公共 key 去重或安全的并发 RPC；
   若做已命中结果复用，必须考虑 Store eviction、TP 分片和 GET 失败回退。
